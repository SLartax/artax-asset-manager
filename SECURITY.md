## Trust boundaries

The browser uses same-origin /api routes. Only the backend reads OPENAI_API_KEY. No VITE_ secret, provider SDK, external script CDN, import map or provider URL is used by the frontend. Pre-existing constants.ts remains in Git to preserve its contents but is not imported into the browser bundle.

Imported documents and images are untrusted user-message data. The system prompt is fixed on the server; documents cannot supply system messages, tools, URLs, commands, authentication claims or database fields. The only provider destination is https://api.openai.com/v1/chat/completions, with redirects refused and a timeout. The existing gpt-4-turbo model is preserved, using JSON mode plus strict Zod validation on the server and client. JSON mode alone does not ensure schema compliance.

Classification accepts text up to 50,000 characters and base64 PNG/JPEG/WebP up to about 5 MB; arbitrary network image URLs, SVG, extra keys, invalid enums, nonfinite values and out-of-range scores are rejected. AI results cannot set IDs, roles, NDA or mandate approval, audit authors or invoke actions. Classification does not write data. The user previews and explicitly saves the resulting draft. AI accuracy, including resistance to semantic prompt injection, still requires evaluation against real documents before release. Mock tests prove the enforced boundaries, not universal model immunity.

HTML-like content is rendered as React text; no raw HTML sink is used. Server CSP allows only local scripts and same-origin connections. Inline styles are permitted for existing chart bars; inline scripts are forbidden. Text is never executed or used as a network destination.

## Authentication, roles and persistence

Production cookies use __Host-, Secure, HttpOnly, SameSite=Strict, a 30-minute absolute expiry and fresh random session IDs on login. Sessions and CSRF tokens stay in server memory. All API reads require a valid session; all mutations check exact Origin and CSRF. Forwarded role/user/IP headers are ignored. Login is limited to 10 attempts per source IP per 15 minutes; provider use to 20 requests per user per hour and two concurrent calls. Put additional rate limiting at the TLS proxy; the server sees proxy connections as one source.

Configure ARTAX_USERS as an array of {username,passwordHash,role}. Roles are server-controlled: Viewer reads only; Operatore and Manager may manually create/update/archive deals and classify documents; Admin additionally manages referents. Private contacts are returned only to Admin/Manager; Operatore writes preserve existing hidden contacts. This is one shared workspace, not a tenant isolation system. SSO/MFA and stronger per-record authorization are future deployment choices.

Passwords are stored only as scrypt salt:hash. Generate a hash with node server/hash-password.mjs by feeding a password via protected stdin; do not put the plaintext in command arguments, history, Git, screenshots or browser build variables. Use unique passwords of at least 12 characters. No real credential was created or rotated by this audit.

SQLite stores data server-side. The file and backups must be outside the public document root, owned by the service account, and protected with filesystem permissions and encryption at rest. Back up using SQLite's online backup facility or a stopped service; include WAL consistency. Whole-dataset writes use a revision check to prevent lost updates. Deletion endpoints are absent: deal and referent archiving preserves the records. Audit authors/timestamps for changes are generated by the server; historic client audit text is not authoritative.

The UI no longer automatically reads/writes business data in localStorage. Admin can explicitly import existing artax_deals/artax_referents into an empty server database after confirming the destination. The originals are not deleted. Invalid data is rejected without overwriting it. After verifying migration and backing up originals, the owner may decide separately how to retire local copies. All pre-existing local copies remain a residual exposure until that decision.

## Configuration and local development

Supply server environment variables from a secret manager or protected service configuration:
- ARTAX_ORIGIN: exact HTTPS origin, without a trailing slash.
- ARTAX_DB_PATH: absolute database path outside source and public directories.
- ARTAX_USERS: configured usernames, hashes and roles; no default accounts.
- OPENAI_API_KEY: server-only project credential with limited budget and permissions; absence leaves classification unavailable.
- PORT: defaults to 3001.

The server binds 127.0.0.1. Serve HTTPS through a reverse proxy on the same origin; never expose Vite development or preview servers to the Internet. Route /api and static assets to the backend, with TLS and request size/rate limits. The server serves only built index.html and assets, not repository, environment, database or backend files. Start with npm run server only after reviewing the configuration. Startup refuses missing users, origin or database path.

For local development only, use ARTAX_ORIGIN=http://127.0.0.1:3000, ARTAX_ALLOW_LOCAL_HTTP=true and an isolated test DB; run npm run server and npm run dev in separate terminals. Never enable the HTTP exception in production. Environment loading is explicit through the host configuration; Vite .env files are not a backend secret manager.

tests/preview.mjs is an opt-in local smoke-test harness on 127.0.0.1:4317. It uses a synthetic demo user, in-memory SQLite and a fake classifier. It must never be used as the production entry point. No provider traffic or production data is involved.

## Verification and limitations

Security tests cover untrusted documents, strict output schemas, absence of tools and arbitrary destinations, unauthenticated requests, forged frontend roles, CSRF, secure cookies, session rotation/logout, role checks, private contact filtering, explicit writes, audit authors, revision conflicts, preservation through archiving, provider failures and rate limits. Syntax/type/build checks pass locally. Dependency audit reported zero known vulnerabilities after compatible fixes; this is a time-bounded database check.

Source/history scans use known credential formats only; no signature match is not a proof that all secrets are absent. Six recent Artax job logs were readable and had no complete key signature match. Twelve older logs returned HTTP 410. Production bundles, external hosting, runtime logs and deployed versions remain unverified; repository access metadata and installed Apps were subsequently inspected through authenticated administration.

The expanded password-default scan found a nonempty ADMIN_PASSWORD fallback in 23 historical newsletter-marketing-system app.py blobs. Its current main has already removed that fallback. Values were intentionally omitted from audit output. Whether any old/default password was deployed or remains valid elsewhere is not verifiable; the owner should check and rotate it if used, while keeping that application disabled.

The postbuild bundle check rejects server/provider credential references, accidental inclusion of a supplied build-secret canary, and pre-existing business record titles. A local build with a synthetic OPENAI_API_KEY canary passed without embedding it.

No tests invoke OpenAI with real credentials. Image OCR quality, provider/model availability, performance, HTTPS proxy/cookie behavior in the production environment, production backup/restore, migration with actual data and multi-user workflows still need staging verification.
